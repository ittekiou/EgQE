## 01｜検証は一つの営みではなかった

P02の共同声明では、検証の結果が四つの基準に整理されていた。P03では、その検証に関係する複数の営みが、個別の記録として現れている。

| 検証対象・方法 | P03の報告 |
|---|---|
| ソースコードのコンパイル | 175,187モジュール、エラーなし |
| 五定理の公理依存性 | 三つの標準公理のみ |
| Mathlibのコンパイル済みファイル | 公式キャッシュと一致 |
| 別環境での再ビルド | 成功 |
| 証明エクスポートの再現 | バイト単位で一致 |
| 命題の比較 | 五定理について一致を確認 |
| 複数のカーネルによる検査 | 受理を報告 |
| leancheckerによるモジュール単位の検査 | 175,187モジュールすべてについて成功 |
| lean4leanによるモジュール単位の検査 | 175,182件が既定設定で成功。残る5件は既定のステップ上限に達し、上限を引き上げた再実行で成功 |
| 一部の検証器・実行条件 | 検査辞退・適用不能・実行継続中 |

P03は、すべての検証を一律に成功として報告しているわけではない。成功したもの、受理されたもの、適用できなかったもの、まだ終わっていないものが、それぞれ記録されている。この違いを消さずに読むことが、観測の出発点になる。

最終的な検証結果が同じであることと、そこに至る検証過程が同じであることも区別しておく。

## 02｜受理しなかったことと、棄却したこと

| 検証器・版 | 検証内容 | 結果 |
|---|---|---|
| con-leche master `cd2eceab` | 全証明エクスポート | accepts |
| con-leche compare `5dc36dc1` | challengeとsolutionの比較 | accepts |
| con-ron master `3f22699b` | challengeとsolutionの比較 | accepts |
| Lean v4.36.0同梱のcon-leche・con-ron | 証明の検査 | declined |
| Lean v4.36.0同梱のlean4lean | v4.33のライブラリの読み込み | not applicable |

同梱版のcon-lecheとcon-ronについて、P03は次のように記している。

> exit 2, not a rejection

P03は、これを証明の棄却ではないと明記している。同梱された古いバイナリが、証明に含まれる一つの反射的帰納型（reflexive inductive type）に対応していないためだと説明されている。一方、masterからビルドされた版については、対応する検査が成功したと報告されている。

ここでは、少なくとも三つを区別する必要がある。

- **証明を受理すること。**
- **証明を棄却すること。**
- **証明を検査できないこと。**

検証器が証明を受理しなかったという記述だけでは、後二者の区別が失われてしまう。

P02とP03の記述は、異なる版や実行条件を区別することで両立しうる。ただし、P02が参照した個々の検証とP03の各実行記録との厳密な対応は確認していない（09を参照）。

## 03｜何が再現されたのか

P03には、別のマシンで、ネットワーク接続を遮断し、ソースを読み取り専用にした環境で再ビルドを行ったという記録がある。

| 項目 | P03の報告 |
|---|---|
| 一致したコンパイル済みファイル | 175,186 / 175,187（不一致1件） |
| 証明エクスポート | 全バイト一致（61,570,595,788 bytes） |

一つのコンパイル済みファイルが一致しなかった。しかし、証明エクスポートは一致した。

P03の留保事項では、その不一致について、並列処理の順序によって自動生成される補題の束縛変数名が変わるためだと説明されている。同一条件で六回コンパイルすると、二種類の出力が四回と二回現れたという。さらに、単一スレッドでのコンパイルでは、六回とも同じ出力が得られたと報告されている。

P03によれば、変数名の違いはカーネルによる検査には影響せず、当該補題は五定理の証明エクスポートにも含まれていない。

### ビルドした場所

P03によれば、175,187個のコンパイル済みファイルのうち98,219個には、ソースファイルの絶対パスが含まれている。残る76,968個には、そのパスが含まれていない。

そのため、コンパイル済みファイルのハッシュを比較する場合には、ビルドを行ったディレクトリも問題になる。同じソースコードを用いたことだけでは、同じハッシュが得られるとは限らない。

### 非決定性の来歴

P03は、一つのファイルに生じた非決定的な挙動について、Leanにおける既報の競合とその修正にも言及している。

- Issue #15498
- Pull Request #15499
- 修正が初めてリリースされた版：v4.36.0

P03は、複数の版を用いた再現実験についても報告している。ただし、これらのissue、pull request、再現用コードについては、今回の観測では直接取得・照合していない。

### 再現の水準と条件

| 水準・条件 | 観測されるもの |
|---|---|
| ビルド環境 | ディレクトリ、使用する版、並列処理など |
| ファイル | バイト列・ハッシュの一致 |
| 形式的内容 | 論理的内容の同一性 |
| 証明エクスポート | 検証対象として取り出されたデータの一致 |
| 検証結果 | 検証器による判定 |

P03自身が、異なるハッシュの証明エクスポートが生成されたとしても、双方がすべての検査を通過しうる場合について述べている。

したがって、生成されたデータの同一性と検証結果の同一性との区別は、今回の観測者が初めて導入したものではない。**P03自身の記述に現れている区別である。** われわれは、その区別を再現性についての観測点として取り出している。

再現性を否定するための区別ではない。何についての再現性なのかを明らかにするための区別である。

ここでの技術的説明はP03による報告に基づく。観測者が不一致の生じたファイルや再現用コードを実行して確認したものではない。

## 04｜同じ検証に、異なる時間がかかる

P03では、Leanの標準カーネルとparanoidカーネルについて、同じバイナリと同じ証明エクスポートを用いながら、メモリ管理に関する環境設定を変更した実行結果が記録されている。

| カーネル | 既定設定 | 設定変更後 |
|---|---|---|
| 標準カーネル | 48時間03分 | 9時間08分 |
| paranoidカーネル | 72時間20分 | 10時間00分 |

いずれも1スレッドで実行。P03では全四件について受理を報告している。

所要時間の比は、標準カーネルで約5.3倍、paranoidカーネルで約7.2倍となる（響詠による算出）。P03は、この設定変更によって検証対象そのものは変わらないと説明している。

何を検証するのか。どのような環境で検証するのか。検証にどれほどの時間がかかるのか。これらは関係しているが、同じ問題ではない。

第四篇では、論理の連鎖の長さとコードの行数を区別した。ここではさらに、検証の内容と検証の所要時間を区別する必要がある。

## 05｜何についての証明なのか

| 定理 | 記述されている対象 |
|---|---|
| `riemannHypothesis` | Mathlibのリーマン予想 |
| `riemannZeta_eq_zero_re` | 同じ命題を展開して記述したもの |
| `LFunction_ne_zero_of_half_lt_re` | ディリクレL関数の臨界線右側での非零性 |
| `LFunction_eq_zero_re` | 臨界帯内の零点についての命題 |
| `LFunction_eq_zero_re_of_isPrimitive` | 原始指標についての対応する命題 |

五つの定理が検証されたという報告は、五つの独立した数学的難問が解決されたという意味ではない。

P03は、GRHについての検証範囲も明記している。ディリクレL関数については、すべての法と指標が対象になっている。一方、デデキントゼータ関数、ヘッケL関数、一般の保型L関数についての命題は、検証対象に含まれていない。

P01では一般化リーマン予想という名称が登場していた。観測標本01ではディリクレL関数の場合という限定が付されていた。P03では、その限定に対応する具体的な命題が提示されている。

**名称によって証明対象を示すことと、命題によって証明対象を特定することは違う。**

## 06｜検証するために、証明を使う

P03は、Mathlibにおけるゼータ関数の定義に依存しない検査として、Alpögeの証明をRobin1984という別の形式化と組み合わせたと述べている。その結果として、三つの算術的帰結が提示されている。

| 帰結 | 接続に用いられた関係 |
|---|---|
| Robinの不等式 | RHとの同値関係 |
| Lagariasの不等式 | RHとの同値関係 |
| 円分体に関する補正されたイデアル版Robin型不等式 | ディリクレL関数についてのGRHとの同値関係 |

三つ目の帰結については、`dirichletGRH_iff_cyclotomicCorrectedIdealRobin` という定理が明示されている。

P03は、Robin1984そのものについても、組み合わせた証明についても、検証結果を報告している。

ここでP03自身が述べている作業の位置づけは、検査である。

この検査は、P02の第一基準である命題の適切さの確認とも関係していると考えられる。ただし、この関係づけは今回の観測者によるものである。

また、ゼータ関数の定義に依存しない検査であることは、Mathlibの定義一般から独立した検査であることを意味しない。P03自身も、算術的帰結がMathlibの別の定義やRobin1984の証明に依存することを明記している。

そのうえで、この作業を第三篇で導入した証明の作動という観点から読んでみる。証明を検査するために、その証明を別の形式化の前提として用いる。検査するという営みが、同時に、証明を別の営みのなかで作動させることにもなっている。

ここでは、検証と作動を区別することが、両者を切断することにはならない。

ただし、その作動の数学的妥当性をわれわれが独立に確認したわけではない。

## 07｜短い命題の背後にあるもの

P03は、カーネルが検査するのはソーステキストそのものではなく、Leanのエラボレータ（ソースの記述を、カーネルが検査する内部の項に変換する処理系）によって生成された項であると説明している。

さらに、三つの算術的帰結について、命題の意味が依存している宣言の数を記録している。

| 命題 | 意味が依存する宣言数 |
|---|---|
| Robinの不等式 | 2,050 |
| Lagariasの不等式 | 1,801 |
| 円分体についての命題 | 7,616 |

P03の計数による。証明の長さではなく、命題の意味についての依存関係を数えたもの。

短く書かれた命題が、少数の前提だけで意味をなしているとは限らない。一方、依存する宣言が多いことは、その命題を証明することが難しいという意味でもない。

命題の記述の長さ。命題の意味を成立させている定義の広がり。命題を証明する論証の長さ。それらを検証するための時間。ここでも、異なるものが数えられている。

P03自身が、三つ目の命題が短く記述されているのは、定義を通して述べられているからであると説明している。その定義を展開した記述は数百行に及び、命題の意味は7,616個の宣言に依存すると報告されている。

したがって、命題の表面的な記述の長さと、その意味を成立させている依存関係の広がりとの区別は、P03自身の記述に由来する。われわれは、この区別をInvisible Groundという観測上の問いに接続している。

依存関係を計数したのはP03の記録主体であり、それをグラウンドについての問いに接続しているのは今回の観測者である。依存関係の可視化を、グラウンド全体の可視化と同一視しない。

## 08｜検証を可能にするグラウンド

P03には、再検証のための手順が公開されている。その手順について、およそ100 GBのRAMと70 GBのディスク容量が必要だと記載されている。ソースからビルドしたcon-lecheの `--compare` による独立検査については、約50 GBのRAMを必要とし、64スレッドで4分未満だったと報告されている。

検証手順が公開されていること。検証に必要な資料が取得できること。検証を実行できる環境があること。実際に検証を行うこと。これらは同じではない。

形式的な検証可能性と、その検証を実際に行える条件との関係も、観測対象として残しておく。

P03の検証作業において、Claude Codeがどのような役割を担ったのかについては、具体的な作業分担が記述されていない。

- AIが証明に関与すること。
- AIが証明の検証に関与すること。
- AIが検証結果の記録に関与すること。

三つを区別しておく。P03から確認できるのは、検証作業がClaude Codeを用いて行われたという記述までである。

## 響詠の端材メモ

175,187個のファイルのうち、一つだけ一致しなかったという記録がある。再現しなかったことが記録され、その再現しなかった理由を調べるための別の営みが始まっている。P03によれば、その非決定的な挙動を再現するためのコードまで用意されている。

**再現しなかったことを、再現する。**

何が再現しなかったのかを区別することで、何が再現されたのかが、より明確になっている。

P03の更新日時の時点では、まだ実行中の検証がある。P02では共同声明が出ている。P03では検証が続いている。認定がなされたことと、検証する営みが終了したことは違う。

P03の算術的帰結について、響詠は最初、検証を終えた証明が次の営みの前提になっている、と読んだ。ところが、P03自身の記述では、**次の営みの前提として用いることが、検証することにもなっている。** 検証してから使う、という一方向の時間ではない。使いながら検証する。これを一般的な数学的営みの構造として確定するのはまだ早いが、少なくとも今回の記録には、そのように読める具体的な作業がある。

ソースコードが同じでも、どこでビルドしたかによってファイルのハッシュが変わる。場所が、生成物の内部に痕跡として残っている。一方、P03によれば、コンパイル済みファイルの不一致にもかかわらず、証明エクスポートは一致していた。場所の痕跡が残る生成物もあれば、その痕跡を含まない生成物もある。

**グラウンドの痕跡が残っていないことと、グラウンドに依存していないことは違う。**
